\section{MLIR}

\fehr{Technically it is used for heterogeneous computing, but it is also used in many other
contexts, such as fully homomorphic encryption or general purpose compilation (clang). It is just
mainly used to build industry compilers.}
MLIR (Multi-Level Intermediate Representation) is an extensible compiler framework that allows
users to define IRs named dialects. Developed as a sub-project of LLVM it aims to facilitate the 
construction of domain specific compilers and improve compilation for heterogeneous computing.
One feature worth highlighting is the interoperability of dialects, allowing any dialect to be
used within any MLIR program.


\fehr{single static assignment -> static single-assignment. Also introduce the acronym SSA.}
The main computation unit in MLIR programs are operations, which have a set of operands (variables),
attributes (static data), and results. Programs are a series of operations which can come from 
multiple dialects, they also have types, which are verified to ensure the program is well formed. 
%
In order to make dataflow information explicit, which makes optimization much easier, MLIR enforces
single static assignment, that is each value is defined exactly once (as a result of an operation), 
and will never be reassigned.
%

as well as \textcolor{teal}{operation type}, and \textcolor{magenta}{result type}:

\subsection*{PDL}

PDL (Pattern Definition Language) is a dialect used in order to define rewrite
patterns. Such patterns can be used in order to transform code.
%
This will be the primary method used to create a backend as PDL patterns can be applied efficiently
by a generic algorithm, and can be checked for correctness using the tools that we will develop. 
After obtaining a series of PDL rewrites for our IR, we can convert that into a lowering.
%
For example a the PDL pattern below converts the LLVM IR equality example above into the RISC-V 
instructions below:
\begin{minted}{mlir}
pdl.pattern : benefit(1) {
  %0 = pdl.type : i64
  %1 = pdl.operand : %0
  %2 = pdl.operand : %0
  %3 = pdl.attribute = 0 : i64
  %4 = pdl.type : i1
  %5 = pdl.operation "llvm.icmp" (%1, %2 : !pdl.value, !pdl.value)
       {"predicate" = %3} -> (%4 : !pdl.type)
  %6 = pdl.result 0 of %5
  pdl.rewrite %5 {
    %7 = pdl.type : !riscv.reg
    %8 = pdl.operation "riscv.sub" (%1, %2 : !pdl.value, !pdl.value) 
        -> (%7 : !pdl.type)
    %9 = pdl.result 0 of %8
    %10 = pdl.attribute = 1 : si12
    %11 = pdl.operation "riscv.sltiu" (%9 : !pdl.value) {"immediate" = %10} 
        -> (%7 : !pdl.type)
    %12 = pdl.result 0 of %11
    pdl.replace %5 with (%12 : !pdl.value)
  }
}
\end{minted}

At the base of the entire project sits the idea of formal semantics for our dialects.
We need to express how our instructions act on their inputs, and we want the semantics
to be easy to work with using automatic solvers. Therefore we use SMT formulas and model
our instructions as bitvector transformations. We also primarily care about basic arithmetic

\subsection{Refinements}

\label{prep-refinements}

Dialects don't always work on the same types of values (RISC-V dialect uses registers, and LLVM IR 
uses integers), checking if a lowering is ``correct'' isn't as easy as saying that for all inputs
the programs yield the same outputs. In fact, we need to introduce the following \emph{refinement}
relation. A program is a \emph{refinement} of another if the following proposition holds:
\begin{equation*}
\text{\emph{target inputs refine the source inputs}} \implies \text{\emph{target outputs refine the source outputs}}
\end{equation*}

Formally this is done by building an expression representative of the refinement relation above 
making use of the programs semantics and a chosen refinement scheme for the source and target values,
and then wrapping it in universal quantifiers. 
We also need to refer to any existentially quantified values that are defined using 
\texttt{smt.declare\_const}, used to represent arbitrary constants. 
We do this by moving all such operations before the \texttt{smt.forall} block.
%
Thus our SMT expression will look something like the following, where operation and type names are
placeholders for the types and operation of the programs:

\begin{minted}{mlir}
// Declare any constants used in the semantics
%0 = smt.forall {
^bb0(%src_lhs : !smt.any_type, %src_rhs : !smt.any_type, 
    %trg_lhs : !smt.any_type, %trg_rhs : !smt.any_type):

  // Evaluate operations to obtain results
  %src_result = "SRC_SEMANTICS"(%src_lhs, %src_rhs) 
    : (!smt.any_type, !smt.any_type) -> !smt.any_type
  %trg_result = "TRG_SEMANTICS"(%trg_lhs, %trg_rhs) 
    : (!smt.any_type, !smt.any_type) -> !smt.any_type

  // Evaluate if operands refine source operands
  %lhs_precondition = "CHECK_REFINEMENT"(%trg_lhs, %src_lhs) 
    : (!smt.any_type, !smt.any_type) -> !smt.bool
  %rhs_precondition = "CHECK_REFINEMENT"(%trg_rhs, %src_rhs) 
    : (!smt.any_type, !smt.any_type) -> !smt.bool
  %valid_inputs = smt.and %lhs_precondition, %rhs_precondition

  // Evaluate if result refine source result
  %valid_output = "CHECK_REFINEMENT"(%trg_result, %src_result) 
    : (!smt.any_type, !smt.any_type) -> !smt.bool

  // The refinement relation
  %is_refined = smt.implies %valid_inputs, %valid_output
  smt.yield %is_refined : !smt.bool
}
\end{minted}

\fehr{There are operations (like "arith.select") that do not propagate poison, even though most
operations do.}
This way we can meaningfully talk about lowerings. Notice that what it means for a value to 
\emph{refine} another is up to the refinement scheme chosen, however a clear example arises when 
considering poison in LLVM. Poison is a form of undefined behavior that propagates, i.e. if any of 
the operands of an operation are poison, than so is the result, while some operations generate 
poison (like an overflowing integer addition). This is useful because it can be used to optimize 
certain code sequences, as we can always assume that poisoned values are convenable for optimization, 
since they are the result of undefined behavior. Looking at the following example, which checks if $x+1 > x$:

\begin{minted}{mlir}
llvm.func @f(%x: i32) -> i1 {
  %one = llvm.mlir.constant(1 : i32) : i32
  %add = "llvm.add"(%x, %one) {overflowFlags = #llvm.overflow<nsw>} 
      : (i32, i32) -> i32
  %cmp = llvm.icmp "sgt" %add, %x : i32
  llvm.return %cmp : i1
}
\end{minted}

\fehr{"Asserting that the poisoned value is true" -> "Asserting that the poisoned value can be compiled to true"}
Because of poison, this code can be optimized to, as we can ignore the undefined behaviour that
arises when $x = \texttt{INT\_MAX}$ by simply asserting that the poisoned value is \texttt{true}:
\begin{minted}{mlir}
llvm.func @f(%x: i32) -> i1 {
  %one = llvm.mlir.constant(1 : i1) : i1
  llvm.return %one : i1
}
\end{minted}

We can now see an useful refinement for poison: any value \emph{refines} poison. But before we explain
how this is checked we first need to introduce the semantics of integers. Because any value can be poisoned
each integer is encoded as a pair of its actual value and a boolean representing its poisoned status.
xdsl-smt has a useful abstraction for this in \texttt{!smt.utils.pair} (the product type), 
together with \texttt{smt.utils.first} and \texttt{smt.utils.second}, representing the projection of 
the first and second elements respectively.

Formally, when checking if an integer refines a potentially poisoned integer value we use the following
expression (using 32 bit integers here as an example):
\begin{minted}{mlir}
%value = smt.utils.first %int_or_poison : (!smt.utils.pair) -> !smt.bv<32>
%poison = smt.utils.second %int_or_poison : (!smt.utils.pair) -> !smt.bool
%is_eq = smt.eq %value %int : (!smt.bv<32>, !smt.bv<32>) -> !smt.bool
%not_poison = smt.not %poison : (!smt.bool) -> !smt.bool
%refines = smt.and %not_poison, %is_eq : (!smt.bool, !smt.bool) -> !smt.bool 
\end{minted}

\subsection{Verifying rewrites}
One benefit of having access to SMT semantics for our dialect is leveraging SMT solvers to 
prove properties about different expressions. For our purposes we prove that our output program 
is a refinement of our input program. So we can exhaustively search the program space until
an equivalent program is found. This also gives us confidence in the correctness of our lowering,
as the SMT solver ensures that the translation is valid for all inputs.

\section{Superoptimization and Lowering Synthesis}

\fehr{You talk about superoptimization but the section is about lowering synthesis.}
As mentioned in \ref{background}, superoptimization is a technique where a compiler 
attempts to find the optimal sequence of instructions that has the same semantics as a source
sequence. One technique used to do this is via exhausting search over the program space and boolean 
tests to prove equivalence of the source and target.
%
Superoptimization has been used to successfully find new optimizations both offline, and to improve
programs by running it as a compilation pass. Some very popular compilers have 
implemented and used this technique, like gnu superoptimizer for x86 assembly \cite{gnu-superopt},
and souper for LLVM IR \cite{souper}.


Lowering synthesis is a similar concept, but instead of searching for optimizations it searches
for valid lowerings between dialects. This is the novel idea behind the project, with the aim of
evaluating the efficiency and exploring the benefits of this technique.
%
The premise is simple, incur one large computational cost once for each source-target pair 
in order to search and find a safe lowering. This is obviously useful when compiling
to low level dialects that need to be lowered to various ISAs.
%
This reduces the number of bugs, but it also opens the door for the easy extension of the 
infrastructure with superoptimizers and other verification tools.

\section{Formal Verification}

In this work, we establish some semantics for RISC-V, so we can talk about the correctness
of a lowering. We take as a source of truth, semantics defined in the sail language \cite{sail-paper}.
Because we will be using these semantics to automatically generate proofs using traditional tools
like SAT and SMT solvers we these to be bitblastable, i.e the bit vector expression can be converted
into expressions about individual bits before being passed into these tools. In particular, we 
use hand-written semantics in Lean, that are proven equivalent to the source of truth. \cite{riscv-lean}
%
Lean is a proof assistant which is used to obtain machine verified theorems. In order to achieve
a satisfactory level of correctness for our semantics we require Lean theorems that prove the
equivalences between our established RISC-V semantics and those we deem correct. 

To achieve this we built tools to convert between SMT dialect semantics and bitblastable lean 
functions we we then used to write the desired proofs. This gives us great confidence in the 
correctness of our semantics which we use as part of our lowering synthesis process.

\section{Base RISC-V to SMT Semantics}
\label{RISC-V to SMT}

In order to lower a program written in the RISC-V dialect to its SMT semantics, we need to
be able to lower the types of all the primitive values (registers and immediates) together 
with all of the instructions as a sequence of SMT instructions. Thus we need to model for
the RISC-V assmenbly.


\subsection{Converting MLIR Types}

There are only a few types of values we will encounter in RISC-V code, given we are working 
with values in CPU registers, and encoded within instructions they can all be represented as 
bitvectors of appropriate sizes, however they will need to be extended to the same size for 
our smt operations. Register values will be encoded as 64-bit bitvectors, and the 12 bit
immediates and 6 bit shift value attributes that appear in the RISC-V instructions are 
extended to 64 bits to operate together with the registers.

\subsection{Handling different Instruction Types}

RISC-V instructions can be divided into a few different types, based on their structure.
Therefore we can extract the values, apply the appropriate conversion, then use the values
for the SMT semantics.
%
In our implementation we handle the following instruction categories: 

\paragraph{Register-Register Operations} 
We can directly get the values of the registers and convert them to 64 bit bitvectors.

\paragraph{Register-Register Word Operation} 
Since we are using RV64, we also have some operations that are meant to work on a 32-bit word.

The semantics for this are the same as for Register-Register Operations, but the values are 
first truncated to 32 bits, and extended back at the end of the operation.

Example: 
\begin{minted}{mlir}
%op1 =  smt.bv.extract %rs1 from 0 : (!smt.bv<64>) -> !smt.bv<32>
%op2 =  smt.bv.extract %rs2 from 0 : (!smt.bv<64>) -> !smt.bv<32>
// Perform the operation on the truncated operands, yielding %tmp
%res = smt.bv.sign_extend %tmp : (!smt.bv<12>) -> !smt.bv<64>
\end{minted}

\paragraph{Register-Immediate Operation}
We extract the immediate and extend it to a full sized bit vector, which can then operate 
with the register.

Example: 
\begin{minted}{mlir}
%op1 = %rs1
%op2 = smt.bv.sign_extend %imm : (!smt.bv<12>) -> !smt.bv<64>
// Perform the operation on the operands
\end{minted}

\paragraph{Register-Immediate Word Operation}
We sign extend the immediate to 64 bits, than truncate the result, before sign extending it again.

Example: 
\begin{minted}{mlir}
%op1 = %rs1
%op2 = smt.bv.sign_extend %imm : (!smt.bv<12>) -> !smt.bv<64>
// Perform the operation on the operands, yielding %tmp
%tmp2 = smt.bv.extract %rs2 from 0 : (!smt.bv<64>) -> !smt.bv<32>
%res = smt.bv.sign_extend %tmp2 : (!smt.bv<32>) -> !smt.bv<64>
\end{minted}

\paragraph{Register-Register Shift (Word) Operation}
We truncate the shift register (since only the lower bits matter), and then zero-extend it back 
to perform the operation.

Example for 64 bits:
\begin{minted}{mlir}
%op1 = %rs1
%tmp = smt.bv.extract %rs2 from 0 : (!smt.bv<64>) -> !smt.bv<6>
%op2 = smt.bv.zero_extend %tmp : (!smt.bv<6>) -> !smt.bv<64>
//Perform the operation, using op2 as the shift value
\end{minted}

For word operations we use 32 bit bitvectors, truncate rs1, and sign extend the result.

\paragraph{Register-Shamt Shift (Word) Operation} 
Extend the shift value from 6 bits the 64 (32) bits.

Example for 64 bits: 
\begin{minted}{mlir}
%op1 = %rs
%op2 = smt.bv.zero_extend %tmp : (!smt.bv<6>) -> !smt.bv<64>
//Perform the operation
\end{minted}

Again, word operations will have additional truncation of \texttt{\%rs} followed by sign extension of \texttt{\%res}.


\subsection{Exploiting identical semantics}

Across different instruction types we encounter instructions with the same underlying behaviour.
Take for example \texttt{riscv.add} and \texttt{riscv.addi}. Their behaviour can be expressed as a single
\texttt{smt.bv.add} opreration on the relevant values. So, as long as we are careful on how we extract
the values from each instruction we can exploit this similarity so have cleaner and more concise code.
%
Moreover, we also see how many semantics would only differ by the smt operation they perform.
Thus we recognize the following categories:

\stefan{Make a list of instructions, detailing some information about them (including their type), and 
add it to an appendix, reference the appendix here}


\paragraph{Trivial Operations}
These operations can be expressed as a single smt operation.

\begin{minted}{mlir}
// obtain op1 and op2 as SSA Values
%res = smt.OPERATION %op1 %op2 : (!smt.bv<?>, !smt.bv<?>) -> !smt.bv<?>
// convert res to !smt.bv<64>
\end{minted}

The way we obtain the operands and process the result is defined by the instruction type, and
they type of \texttt{?} can be inferred from the types of the operands.

This is a the common case and includes a wide range of operations.


\paragraph{Comparisons}

These require special care as the smt dialect comparison operations yield boolean values
that need to be converted into bitvectors. So semantics for comparison operations look like the
this:

\begin{minted}{mlir}
// obtain op1 and op2 as SSA Values
%res_bool = smt.COMPARISON op1 op2 : (!smt.bv<?>, !smt.bv<?>) -> !smt.bv<?>
%zero = smt.bv.constant #smt.bv<0> : !smt.bv<64>
%one = smt.bv.constant #smt.bv<1> : !smt.bv<64>
%res = "smt.ite"(%res_bool, %one, %zero) :
    (!smt.bool, !smt.bv<64>, !smt.bv<64>) -> !smt.bv<64>
\end{minted}

\paragraph{Other}

Some instructions have completely custom semantics, however with careful implementation
they plugged into the existing instruction types. For example the the \texttt{slli.uw} instruction
which has the following semantics, requiring a trunctation followed by a zero extension:

\begin{minted}{mlir}
%trunc_reg = smt.bv.extract %reg : (!smt.bv<64>) -> !smt.bv<32>
%ext_reg = smt.bv.extend %trunc_reg : !smt.bv<32> -> !smt.bv<64>
%res = smt.bv.shl %ext_reg %shamt : (!smt.bv<64>, !smt.bv<64>) -> !smt.bv<64>
\end{minted}

By building abstractions for these instruction types and common behaviours, we can very easily
implement the semantics for an instruction. This yields an easily extensible framework for 
defining semantics for RISC-V in the smt dialect.

\section{Theorems of equivalence in Lean}

\label{lean theorems}

In order to ensure the correctness of our semantics we programatically create lean4 theorems
to formally prove the equivalence of our semantics to those we consider a source of truth, which
are already written in lean.

We first obtain Lean functions that are representative of our RISC-V semantics, and we use them
as part of our equivalence theorems. First we encode our risc-v instructions into mlir blocks, 
with the arguments being the registers and immediates used by the instruction. Using our lowering to the smt dialect previously defined,
we first lower the block, obtaining the semantics of our instruction. 
%
All that's left is lowering from smt to a lean function, but since lean isn't an mlir
dialect we cannot use xdsl to our advantage when outputing lean code, so we also need to write 
working formatting for our lean functions and theorems.

\subsection{RISC-V to Lean Functions}

Walking through an example, we first start with a RISC-V instruction:
\begin{minted}{mlir}
%0 = riscv.slt %arg0, %arg1 : (!riscv.reg, !riscv.reg) -> !riscv.reg 
\end{minted}

Which gets lowered to semantics:
\begin{minted}{mlir}
%0 = "smt.bv.slt"(%arg0, %arg1) : 
   (!smt.bv<64>, !smt.bv<64>) -> !smt.bool
%1 = smt.bv.constant #smt.bv<0> : !smt.bv<64>
%2 = smt.bv.constant #smt.bv<1> : !smt.bv<64>
%3 = "smt.ite"(%0, %2, %1) : 
   (!smt.bool, !smt.bv<64>, !smt.bv<64>) -> !smt.bv<64>
\end{minted}

The next step is converting the semantics above into a lean function like the following:
\begin{minted}{lean}
let a0 : Bool := (BitVec.slt arg1 arg0) ;
let a1 : BitVec 64 := 0 ;
let a2 : BitVec 64 := 1 ;
let a3 : BitVec 64 := (cond a0 a2 a1) ;
\end{minted}

Thus our program is a series of let bindings for each operation and SSA value. We assign each
value a different ID and convert each element of the source program to a lean equivalent.
%
Types and attributes are straightforward, a \texttt{!smt.bv<X>} gets lowered to \texttt{BitVec X}
constant attributes get lowered directly, and their type is luckily inferred by the lean type checker.
Booleans behave in the same way.
%
We also have a variety of operations, some of which are grouped together when lowering so we can leverage
the similarity of their structure.

\paragraph{Constant Operation}
The source operation:
\begin{minted}{MLIR}
%res = smt.bv.constant #smt.bv<X> : !smt.bv<Y>
\end{minted}
is lowered to:
\begin{minted}{lean}
let res : BitVec Y := X ;
\end{minted}


\paragraph{Standard Binary Operation}
The source operation:
\begin{minted}{mlir}
%res = "smt.OP"(%arg0, %arg1) : (?, ?) -> ResultType
\end{minted}
is converted to:
\begin{minted}[escapeinside=||]{lean}
let res : |\textcolor{cyan}{ResultType}| := |\textcolor{cyan}{OP arg0 arg1}|;
\end{minted}
Where we use \textcolor{cyan}{cyan} to represent the lowered types, arguments and operation names.
%
Examples of binary operations are: \texttt{smt.bv.add, smt.bv.slt, smt.bv.ult} and more, all of which
have a lean equivelent like \texttt{BitVec.add, BitVec.slt, BitVec.ult}.

\paragraph{Shift Operation}
Lean bit vector shift operations use shift values of type \texttt{Nat} so we need to add a 
conversion for shift operations, so:
\begin{minted}{mlir}
%res = "smt.OP"(%arg0, %arg1) : (?, ?) -> ResultType
\end{minted}
is converted to:
\begin{minted}[escapeinside=||]{lean}
let res : |\textcolor{cyan}{ResultType}| := |\textcolor{cyan}{OP arg0}| (BitVec.toNat |\textcolor{cyan}{arg1}|);
\end{minted}

This pattern is used for operations \texttt{smt.bv.shl, smt.bv.lshr} and \texttt{smt.bv.ashr} which have
bitvector equivalents \texttt{BitVec.shiftLeft, BitVec.ushiftRight} and \\ \texttt{BitVec.sshiftRight} respectively

\paragraph{Ternary Operation}
\begin{minted}{mlir}
%res = "smt.OP"(%arg0, %arg1, %arg2) : (?, ?, ?) -> ResultType
\end{minted}
is converted to:
\begin{minted}[escapeinside=||]{lean}
let res : |\textcolor{cyan}{ResultType}| := |\textcolor{cyan}{OP arg0 arg1 arg2}|;
\end{minted}

This pattern is used for operation \texttt{smt.ite} which has the
lean equivalent \texttt{cond}.

\paragraph{Extend Operation}

\begin{minted}{mlir}
%res = "smt.extendOP"(%arg) : (?) -> !smt.bv<X>
\end{minted}
is converted to:
\begin{minted}[escapeinside=||]{lean}
let res : |\textcolor{cyan}{ResultType}| := Bitvec.|\textcolor{cyan}{some}|Extend X |\textcolor{cyan}{arg}|;
\end{minted}
Where \emph{\texttt{start}} and \emph{\texttt{end}} are attributes of the source operation.

This pattern is used for operation \texttt{smt.bv.zeroExtend} and \texttt{smt.bv.signExtend}.

\paragraph{Extract Operation}

\begin{minted}{mlir}
%res = smt.bv.extract %arg from ? : (?) -> ResultType
\end{minted}
is converted to:
\begin{minted}[escapeinside=||]{lean}
let res : |\textcolor{cyan}{ResultType}| := BitVec.extractLsb |\emph{start} \emph{end} \textcolor{cyan}{arg}|;
\end{minted}
Where \emph{\texttt{start}} and \emph{\texttt{end}} are attributes of the source operation.

We use the patterns above to recursively lowers all operations from the semantics block into an 
appropriate Lean function.

\subsection{Proving theorems with bv\_decide}

After succesfully obtaining a lean function for the RISC-V instructions semantics we formulate 
equivalence theorems like the following, usinging the bv\_decide tactic, which leverages the 
bitblastable nature of the semantics and invokes a SAT solver to automatically generate a proof
for the theorem, which gets checked by Lean.

The theorems will take the same shape, first using the unfold tactic to replace the let bindings
with their underlying expressions, followed by bv\_decide, which finishes the proof:
\begin{minted}{lean}
theorem OP_eq (a0 : BitVec 64) (a1 : BitVec 64) 
    : RV64.OP a0 a1 = _OP a0 a1 := by
  unfold [RV64.OP, _OP]
  bv_decide
\end{minted}
Here, \texttt{\_OP} is the name of the function we automatically printed, and \texttt{RV64.OP} is
the functions which we consider a source of truth.

\section{RISC-V Enumeration}

\label{enumeration}

To achive our goal of backend synthesis we require a method of enumerating the RISC-V program space.
Thus we levereged and modified the mlir-fuzz tool to allow for exhaustive enumeration of RISC-V programs.
This was done by implementing the dialect in IRDL, to provide mlir-fuzz with the operation definitions, 
and extending the enumeration with `synthetic operations' which have `holes' for attributes 

\subsection{RISC-V in IRDL}

The RISC-V dialect is a work in progress implementation as part of the xDSL project, therefore
when working with mlir-fuzz, which is a project written in C++ working with MLIR, we used
opaque types when refering to registers. This is achieved by adding a new configuration for 
the dialect in mlir-fuzz, and handling the edge cases with care.

Example of a basic operation defined in IRDL:
\begin{minted}{mlir}
irdl.operation @add {
  %register = irdl.is !riscv.reg
  irdl.operands(operand0: %register, operand1: %register)
  irdl.results(result0: %register)
}
\end{minted}

\subsection{Synthetic Operations}

Many RISC-V operations use attributes to encode constants. Take for example the average "riscv.addi"
operation which contains a 12 bit immediate. When synthesizing a backend we want to be able to 
use such immediates to our advantage, as that increases the amount of behaviours we can synthesize,
however enumerating a different program for all $2^12$ possible values of our constant would be too computationally intensive.

\begin{minted}{mlir}
%res = riscv.addi %arg 42 : !riscv.reg -> riscv.reg
\end{minted}
%
Therefore during our synthesis process we want the ability to infer constants using the SMT solver's
capability. To achieve this during enumeration we are going to replace operations that use attributes 
with a `synthetic form'. These \texttt{synth.op}s contain the information to build an instance of 
the underlying operation, but they can be lowered differently to allow the SMT semantics
to have an ``unknown'' variable that a solver can find a solution for.

\begin{Verbatim}[commandchars=\\\{\}, fontsize=\small]
\textcolor{red}{%res} = "synth.op"(\textcolor{green!50!black}{%op...}) <\textcolor{blue}{op_name = \emph{name}}> \{\textcolor{orange}{attr : type, ...}\} : \textcolor{teal}{(!type)} -> \textcolor{magenta}{!type}
\end{Verbatim}

As we can see in the example above a synthetic op contains the \textcolor{blue}{original operation name},
\textcolor{green!50!black}{operands}, \textcolor{orange}{a dictionary containing attribute names and 
their desired types}, \textcolor{teal}{the operand types} and \textcolor{magenta}{the result types}.

To obtain the attribute types for emmiting synth ops, we would need to parse them from the IRDL constraints.
Unfortunately, IRDL doesn't yet have the expressivity to handle arbitrary types for
attributes. As a workaround we resorted to using a fixed value for immediates (usually zero)
so the operation has the correct shape, which would be ignored when emmiting synthetic operations.
To identify which operations are meant to be emmited using this method we marked them with the IRDL
attribute \texttt{synth}.
\begin{minted}{mlir}
irdl.operation @addi attributes {synth} {
  %register = irdl.is !riscv.reg
  %imm = irdl.is 0 : si12 
  irdl.operands(operand0: %register)
  irdl.results(result0: %register)
  irdl.attributes {"immediate" = %imm}
}
\end{minted}

Synthetic operation allow for the usage of arbitrary smt constants for the values that would
normally be represented by the attributes. For example we have the following lowering from
a synthetic add to the semantics, where we use a \texttt{smt.declare\_const} instead of the
attribute.

\begin{minted}{mlir}
%res = "synth.op"(%op) <op_name = riscv.addi> {immediate : si12} 
    : (!riscv.reg) -> !riscv.reg
\end{minted}
To:
\begin{minted}{mlir}
%imm = smt.declare_const : () -> !smt.bv<12>
//... (some additional operations used to reconstruct the transformation)
%imm_ext = smt.bv.signExtend %imm : !smt.bv<12> -> !smt.bv<64>
%res = smt.bv.add %op %imm_ext : (!smt.bv<64>, !smt.bv<64>) -> !smt.bv<64>
\end{minted}
This leaves a hole, that the smt solver will be able to fill with an appropriate constant if one
exists that leads to a correct lowering.

\section{Backend Synthesis}

\label{backend synthesis}

We use the tools implemented thus far to synthesise a backend from a the arithmetic subset of 
LLVM IR dialect instructions to the RISC-V dialect. To achieve this we efficiently
enumerate the search space, validate valid lowerings, reconstruct the lowering by eliminating
synthetic operation, than generate a PDL Pattern for the lowering that can then be applied to 
arbitrary programs.

\subsection{Multithreaded Enumeration}

\stefan{Elaborate on how a lowering gets generated in the first place}
To efficiently make use of the available compute we exploit the inherent division of the lowering
task, on an instruction by instruction basis. Thus, we use an executor pool to run many tasks in 
parallel and create a new job for every single operation our source set. The highly parallelisable
nature of the task at hand means that it can make very effective use of high performance compute
clusters.

We also want to be able to stop once we find a correct translation, as to not waste compute resources. 
We achieve this by performing iterative deepeing on the size of our programs, i.e. we 
first generate the programs with 1 operation, then we generate programs with up to 2 operations 
and so on. This way, if we find a valid lowering for an instruction we are sure it is optimal, 
as we had previously failed finding a lowering with any smaller program.


\subsection{Refinements}
\label{impl-refinements}

After exhaustively enumerating the programs in the searh space, the next step in the backend synthesis
process involves confirming whether the target program is a refinement of the source. 
As presented in \ref{prep-refinements} after lowering the programs to their semantics in the SMT dialect 
we construct an SMT expression that is true if and only if our refinement relation below holds for 
all possible inputs.

\begin{equation*}
\text{\emph{target inputs refine the source inputs}} \implies \text{\emph{target outputs refine the source outputs}}
\end{equation*}

First, we must define a refinement scheme from the values in the source program (which are possibly poisoned
integer values) to RISC-V (64-bit) registers. We can easily imagine how this might work for 64 bit integers, as they
can fully be stored in a register, however there is some room for interpretation when considering smaller
bit width intergers as it is unclear what the upper bits of the register should be.

In this work we identify and analyze two different refinement schemes for our instructions that have 
their own different benefits and drawbacks. One where the upper bits are constrained to a single
possible value (the register becoming the sign extension of the integer), and one where they can
take any value (thus the integer needs to be a truncation of the register). In the following paragraphs
we describe what the refinements in more detail, together with their primary differences and use cases.

\paragraph{Sign extension refinement}

In this refinement scheme, we consider a register to refine a value, if the sign extension 
of the value to 64 bits equals the value held within the registers (the bitvectors match).
If the source value is unsigned, we use the zero extension instead. However this leaves the
values which don't have a specified signedness up to interpretation. In our case we use the
sign extension, although this is an arbitrary choice, as both options yield similar drawbacks.
This approach makes translating comparisons simpler, as we don't have to extend the values
to 64 bits, but it is worse at handling overflows. A more detailed analysis of the effects 
of these refinements on instruction lowerings is found in \emph{\ref{eval-refinements}}.

Formally, when evaluating SMT queries we have the following sequence of SMT operations 
(written here in the SMT dialect) to evaluate whether a register refines an integer type 
value (using 32 bits as an example). As discussed in \ref{prep-refinements}, in the LLVM dialect 
semantics integer values are pairs composed of their value and a bool, which is true if the value 
is poisoned.

\begin{minted}{mlir}
//Here %int repesents an integer of 32 bits and %reg the register values
%value = smt.utils.first %int : (!smt.utils.pair) -> !smt.bv<32>
%poison = smt.utils.second %int : (!smt.utils.pair) -> !smt.bool
%ext_value = smt.bv.sign_extend %value : (!smt.bv<32>) -> !smt.bv<64>
%is_eq = smt.eq %ext_value %reg : (!smt.bv<64>, !smt.bv<64>) -> !smt.bool
%not_poison = smt.not %poison : (!smt.bool) -> !smt.bool
%refines = smt.and %not_poison, %is_eq : (!smt.bool, !smt.bool) -> !smt.bool
\end{minted}

\stefan{Give example of where this is worse.}

\paragraph{Truncation refinement}

This refinement scheme takes the opposite approach, where a register refines a value if 
the truncation of the register to the values bitwidth is equal to that value (i.e the lower
bits of the register are the same as the value in question). This eliminates makes arithmetic
easier, as overflow is handled by the refinement (as the overflow would affect the higher bits
which are truncated when checking for refinements). However comparisons become harder to handle
as the higher bits of the operands could take any value and still be a valid refinement, so
in our lowering we will need to truncate the arguments before performing any comparison between
them.

As an example consider the following translation from:
\begin{minted}{mlir}
%res = llvm.icmp "slt" arg0, arg1 : i8 
\end{minted}
To:
\begin{minted}{mlir}
%res = riscv.slt arg0, arg1 : (!riscv.reg, !riscv.reg) -> !riscv.reg
\end{minted}

Because \texttt{arg0} and \texttt{arg1} need to refine \texttt{i8} they could feasibly take the
values 256 ($2^8 + 0$) and 1. The result of the comparison would be false, however the values are
valid refinements of 0 and 1, which would yield a true result in the source operation. Thus we can say 
that the translation is invalid.

Formally, we use the following sequence of SMT operations to evaluate if a register refines an integer 
value (using 32 bits here as an example):
\stefan{Maybe I should give a brief overview of the dialect instructions in an Appendix}
\begin{minted}{mlir}
//Again, %int repesents an integer of 32 bits and %reg the register values
%value = smt.utils.first %int : (!smt.utils.pair) -> !smt.bv<32>
%poison = smt.utils.second %int : (!smt.utils.pair) -> !smt.bool
%trunc_value = smt.bv.extract %reg from 0 : (!smt.bv<64>) -> !smt.bv<32>
%is_eq = smt.eq %value %trunc_value : (!smt.bv<32>, !smt.bv<32>) -> !smt.bool
%not_poison = smt.not %poison : (!smt.bool) -> !smt.bool
%refines = smt.and %not_poison, %is_eq : (!smt.bool, !smt.bool) -> !smt.bool
\end{minted}

\subsection{Reconstruction}

\stefan{Present current world (technically preparation, but I think it would make more sense here), where
we use synth constants for specific operation. Then proceed with the explanation of how reconstruction is done
for synth ops. Provide a basic example.}

After confirming that a lowering is correct we first need to obtain a valid source and target programs for it.
Since we are using \texttt{synth.op} operations in our search to allow for the generation of arbitrary constants
we must then proceed to reconstruct the target program. When the lowering is found the SMT solver provides a 
model for the constant values it used to fill in the holes form the synthetic operation, however some setup
needs to be done beforehand so that we associate the values provided by the model, to the correct holes left
by the \texttt{synth.op} operations. Thus, when lowering synthetic operations, we first give unique names
to all of the constants and we include some additional operations that carry some information relevant for 
reconstruction, as can be seen here:

\begin{minted}[escapeinside=||]{mlir}
|From:|
%res = "synth.op"(%op) <op_name = source_op> {attr : attr_type, ...} 
    : operand_types -> result_type

|To:| 
//Also keep track of the connection between %name_with_id and the synth.op
%name_with_id = smt.declare_const : () -> !lowered_attr_type
%conv = synth.conversion %name_with_id : !attr_type
%from = synth.from_value %conv {cst_value : "name_with_id"}
//Repeat for every other attribute
//Lower the source_op, using the attributes above
\end{minted}

When obtaining constant from the model they will be associated with the unique name we have given attribute
then we can walk the program searching for all the \texttt{synth.from\_value} operations, which will give
us the relevant \texttt{synth.conversion} operations, which contain the relevant metadata for the reconstruction. 
After converting the bitvector obtained from the model into its integer type we can simply construct the

\subsection{Conversion to PDL}

At this point our tool can succesfully identify correct RISC-V lowerings for our target LLVM dialect
subset. We then make use of PDL by converting the IR programs we have into PDL patterns. To achive 
this we must first decompose the individual source and target programs into their components (attributes, 
operands, results, types and operations) and create patterns for them. Then, we than simply construct
a PDL rewrite rule that the input pattern can be replaced with the output. We take a look of how
the lowering from \texttt{llvm.icmp "slt"} using \texttt{i64} to \texttt{riscv.slt} gets expressed
as a PDL pattern.

\begin{minted}[escapeinside=||]{mlir}
|The source program:|
%res = llvm.icmp "slt" %arg0 %arg1 : i64 

|Becomes:|
%type = pdl.type : i64
%op1 = pdl.operand : %type
%op2 = pdl.operand : %type
//The predicate is represented as an i64
%pred = pdl.attribute = 4 : i64  // "slt"
%res_type = pdl.type : i1
%operation = pdl.operation "llvm.icmp" (%op1, %op2 : !pdl.value, !pdl.value) 
    {"predicate" = %pred} -> (%res_type : !pdl.type)
%result = pdl.result 0 of %operation
\end{minted}

\begin{minted}[escapeinside=||]{mlir}
|Then, the target program:|
%res = riscv.slt %arg0 %arg1 : !riscv.reg

|Becomes:|
%type = pdl.type : !riscv.reg
%op1 = pdl.operand : %type
%op2 = pdl.operand : %type
%res_type = pdl.type : !riscv.reg
%81 = pdl.operation "riscv.slt" (%op1, %op2 : !pdl.value, !pdl.value) 
    -> (%type : !pdl.type)
%result = pdl.result 0 of %operation
\end{minted}

When writing the transformation as a rewrite we need refer to the operands of the source operation,
however this would cause the type checks to fail, as we cannot use integer types in RISC-V operations.
To work around this we make use of the \newline \texttt{builtin.unrealized\_conversion\_cast}, which is an operation
representing an arbitrary type conversion. We can then create a type checking pattern by converting 
the operands to \texttt{!riscv.reg} and the result of the program back to an integer. 

Notice how (in the example below), except those on arguments and results, the \newline
\texttt{builtin.unrealized\_conversion\_cast}s cancel each other out, and thus can be safely removed
when lowering entire programs. The remaining casts, will simply change the type of the function 
that is lowered.

\begin{minted}{mlir}
func.func @add_three(%a: i32, %b: i32, %c: i32) -> i32 {
  %tmp = "llvm.add"(%a, %b) : (i32, i32) -> i32
  %sum = "llvm.add"(%sum1, %c) : (i32, i32) -> i32
  func.return %sum : (i32) -> ()
} 

Becomes:

func.func @add_three(%a: i32, %b: i32, %c: i32) -> i32 {
  %a_reg = builtin.unrealized_conversion_cast %a : i32 to !riscv.reg 
  %b_reg = builtin.unrealized_conversion_cast %b : i32 to !riscv.reg 
  %tmp_reg = "riscv.add"(%a_reg, %b_reg) 
    : (!riscv.reg, !riscv.reg) -> !riscv.reg
  %tmp = builtin.unrealized_conversion_cast %tmp_reg : !riscv.reg to i32

  %tmp_reg2 = builtin.unrealized_conversion_cast %tmp : i32 to !riscv.reg 
  %c_reg = builtin.unrealized_conversion_cast %c : i32 to !riscv.reg 
  %sum_reg = "riscv.add"(%tmp_reg2, %c_reg) 
    : (!riscv.reg, !riscv.reg) -> !riscv.reg
  %sum = builtin.unrealized_conversion_cast %sum_reg : !riscv.reg to i32
  func.return %sum : (i32) -> ()
} 

Which then translates to:
func.func @add_three(%a: !riscv.reg, %b: !riscv.reg, %c: !riscv.reg) 
    -> !riscv.reg {
  //%a, %b, %c casts propagate to argument types

  %tmp = "riscv.add"(%a, %b) : (!riscv.reg, !riscv.reg) -> !riscv.reg
  //%tmp casta cancel each other out
  %sum = "riscv.add"(%tmp, %c) : (!riscv.reg, !riscv.reg) -> !riscv.reg

  //%sum cast propagates to result type
  func.return %sum : (!riscv.reg) -> ()
} 
\end{minted}

\stefan{Introduce the following code snippet}

\begin{minted}[escapeinside=||]{mlir}
%type = pdl.type : i64
%op1 = pdl.operand : %type
%op2 = pdl.operand : %type
%pred = pdl.attribute = 4 : i64  // "slt"
%res_type = pdl.type : i1
%src_oper = pdl.operation "llvm.icmp" (%op1, %op2 : !pdl.value, !pdl.value) 
    {"predicate" = %pred} -> (%res_type : !pdl.type)
%src_result = pdl.result 0 of %src_oper
pdl.rewrite %src_oper {
  %reg_type = pdl.type : !riscv.reg

  %cast_op1 = pdl.operation "builtin...cast"(%op1 : !pdl.value) 
      -> (%reg_type : !pdl.type)
  %op1_reg = pdl.result 0 of %cast_op1

  %cast_op2 = pdl.operation "builtin...cast"(%op2 : !pdl.value) 
      -> (%reg_type : !pdl.type)
  %op2_reg = pdl.result 0 of %cast_op2

  %trg_oper = pdl.operation "riscv.slt" (%op1_reg, %op2_reg 
    : !pdl.value, !pdl.value) -> (%reg_type : !pdl.type)
  %trg_result = pdl.result 0 of %trg_oper

  %cast_res = pdl.operation "builtin...cast"(%trg_result : !pdl.value) 
      -> (%res_type : !pdl.type)
  pdl.replace %src_oper with %cast_res
}
\end{minted}

With this pattern the result of the  \texttt{llvm.icmp "slt"} operation gets replaced with the result
of the \texttt{riscv.slt} operation, and thus is used as part of subsequent lowerings, i.e the source
operands of integer types, get replaced with registers. This allows us to apply all of our patterns, which 
we converted from the lowerings we found as part of our enumerative synthesis.

\emph{Was correctness ensured, if so, how? Are there any limitations to this method? Can

\subsection{Semantics correctness}

As presented before, the semantics are validated using automatically generated Lean proofs.
Therefore for all the arithmetic instructions considered in the base RISC-V instruction set
a lean function was generated from it's lowering to the SMT dialect, which was then proven
equivalent using automated tactics. In particular, we use was made of the unfold and 
bv\_decide tactic, to create theorems like the ones below:

\begin{minted}{lean}
def _slt (a0 : BitVec 64) (a1 : BitVec 64) : BitVec 64 :=
  let a2 : Bool := (BitVec.slt a1 a0) ;
  let a3 : BitVec 64 := 0 ;
  let a4 : BitVec 64 := 1 ;
  let a5 : BitVec 64 := (cond a2 a4 a3) ;
  a5
theorem slt_eq (a0 : BitVec 64) (a1 : BitVec 64) : RV64.slt a0 a1 = _slt a0 a1 := by
  unfold RV64.slt _slt
  bv_decide

def _andi (a0 : BitVec 12) (a1 : BitVec 64) : BitVec 64 :=
  let a2 : BitVec 64 := (BitVec.signExtend 64 a0) ;
  let a3 : BitVec 64 := (BitVec.and a1 a2) ;
  a3
theorem andi_eq (a0 : BitVec 12) (a1 : BitVec 64) : RV64.andi a0 a1 = _andi a0 a1 := by
  unfold RV64.andi _andi
  bv_decide
\end{minted}
The RV64 semantics are taken from the following repository \cite{riscv-lean}.

The correctness proof tool was developed early in the development process. While the author
claims that it has cought a variety of bugs that would have snuck through the manual 
implementation of the semantics. While this claim is difficult to prove, we still mention
it as it was rather surprising to the author.

This approach has two major limitations that, luckily, don't arise within the scope of the 
project. First, there is a requirment for authoritative semantics to be available and written
in Lean. Secondly, no proofs can be made for instructions that have additional effects (reading
and writing from memory), at least not without greatly expanding the complexity of the tools
created.

Other than the limitations mationed above, this method can be easily extended to include
other dialects. However, as part of the implementation a wrapper needs to be created 
to invoke the semantics class of the operation. For RISC-V (and ISAs in general) this is
quite easy as instructions tend to take one of a few different shapes (as a design principle)
so this similarity can be exploited to generate generic wrappers. In particular for the RISC-V
theorems we have a wrapper for operations that take two registers, and those that take an 
attribute and an operand.


\subsection{PDL Transformations}

After having proof of correctness for the semantics of individual instructions we can be confident
that given a particular program, its lowering into the SMT dialect is a correct representation
of its semantics. Therefore, given we construct our SMT expressions to only be satisfiable if
the target program is a refinement of the source, we can be sure that whatever refinement scheme
we define will hold for the lowering, if the SMT solver succesfully finds a model.

This leaves only one point of failure for the correctness of our instruction lowerings, 
the SMT solver itself. In our tools we rely on the Z3 solver, which is a mature 
open-source project. As a result we assume that any output of the solver is correct. However,
we have yet to prove that lowering more than one instruction with our method doesn't introduce
any errors. This can be easily seen as true by considering the refinement relation, and how
2 pairs programs that refine each other compose to create another such pair, i.e it is 
transitive.

% Snuck a commutative diagram in my dissertation :)
\begin{figure}[H]
    \centering
    \begin{tikzcd}
        S_1 \arrow[r, "Source_1"] & S_2 \arrow[r, "Source_2"] & S_3 \\
        T_1 \arrow[u, "\mathcal{R}"] \arrow[r, "Target_1"'] & T_2 
        \arrow[u, "\mathcal{R}"] \arrow[r, "Target_2"'] & T_3 \arrow[u, "\mathcal{R}"]
    \end{tikzcd}
    \caption{Transitivity diagram of the refinement relation $\mathcal{R}$}
    \label{fig:refinement_composition}
\end{figure}

Formally, considering the diagram above, as the refinement relation ($\mathcal{R}$) 
holds for each individual translation step, the outputs of the first valid target operation 
serve as valid refined inputs for the second, guaranteeing that the composed 
target sequence correctly refines the composed source sequence. This can then be extended
to programs of any size by induction.

\section{Refinements}
\emph{What would be appropriate refinements to RISC-V registers? Any advantages or disadvantages of each?}
\label{eval-refinements}

\paragraph{Truncation refinement coverage advantage}

The lowering obtained using truncation scheme gives additional leniancy to instructions
that can overflow into the upper `garbage' bits of the register. In particular this reduces
the required program size for basic arithmetic (\texttt{addi}, \texttt{subi}), as well as 
the logical shift operations like \texttt{shli} and \texttt{shrui}.

\paragraph{Sign extension refinement coverage advantage} Truncation however, struggles greatly
with comparisons on sub-registers, as comparing two 64-bit registers with `garbage' upper
bits yields wrong results. Under the sign extension refinement scheme we are able to 
fully synthesize such comparisons.

\paragraph{Synthesis duration}
When evaluating whether a program is a valid lowering for another the SMT solver can spend
significantly more time when using the sign extension scheme. That is because the queries
generated with this refinement are harder to solve, as Z3 must prove that the equality 
holds for all the bits, including those that were sign extended for which it has little
to no information according to the semantics, meanwhile the truncation queries are much 
faster as large chunks of the work can be discarded as it related to the upper bits,
which are treated as anything. Table \ref{tab:synthesis_duration_comparison} contains
some examples where there is a significant slowdown.

\section{Work Completed}

The project consisted of developing a prototype for a backend synthesis tool, by leveraging
existing work and other open source project, and exploring the feasibility of automated lowering
generation as an option in the compiler designers toolset. Overall, the project has achieved 
it's goal, consisting of a working pipeline that can succesfully generating lowerings from
source operations with well defined semantics to the arithmetic subset of the base RISC-V 
instruction set.

\subsection{Development of tool to check RISC-V semantics in Lean}

We build a tool to translate SMT semantics that were manually written for the RISC-V
ISA into lean theorems that serve as proofs of equivalence between our semantics and
authoritative semantics we asserted as a source of truth.

\subsection{Synthesized part of an LLVM to RISC-V backend}

Using tools implemented, along with existing open source ones, we obtained lowerings from 
a large subset of the Arith dialect (and consequently, the LLVM IR) to the base RISC-V ISA. 
We leveraged mature SMT solvers and formal methods to ensure the lowerings were correct.

\subsection{Novel Contributions}

\paragraph{Evaluated feasability of generating lowerings}

Backend synthesis the novel idea behind the project, as a result we evaluated it's feasability
and limitations in the context of genarating a lowering from a mature IR like LLVM (or Arith)
to a simple ISA like RISC-V

\paragraph{Explored refinement options}
During development the idea of refining integers of various bitwidths into architectural
registers was explored and two feasable lowering schemes were identified. Analysis was
performed to determine their advantages and disadvantages.


\section{Future Work}

\paragraph{Creation of proper tool} 
Using a language like C++ and specialising the code towards backend synthesis could lead
to a significant speed up, as well as an increase in the usability of the tool.

\paragraph{Using heuristics while searching}
Evaluation results (and common sense) showed that synthesis time greatly decreases when we
luckily stumble upon the right answer in the search. A future work could evaluate the impact
of various heurisitcs in our search process, which could yield a large speed up.

\paragraph{Using LLMs to search deeper}
LLMs have showen promising results when asked to generate IR programs. However these have
no guarantee of correctness of optimality. However using the tools from this project, and
xdsl-smt, correctness of the lowering can be proven. As for optimality, by exhaustively 
searching up to a depth of $d$ and not finding a working transformation, we can easily 
prove one of depth $d+1$ found by an LLM is optimal. As a result it could be possible 
to leverage large scale AI models to investigates programs up to one deeper than normal
without sacrificing correctness or optimality.
